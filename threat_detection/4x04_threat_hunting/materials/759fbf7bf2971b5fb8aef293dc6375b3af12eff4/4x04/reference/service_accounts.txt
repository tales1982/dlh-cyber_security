PURPOSE
-------

This matrix defines the authoritative authorization boundaries for every
service account in the meddefense.local domain.  It is the reference
document for answering two questions:

  1. What is this service account allowed to do ?
  2. Where is this service account allowed to authenticate from ?

Any service-account authentication event that violates this matrix is,
by definition, anomalous and requires investigation.  This includes any
interactive logon (Logon Type 2, 10, 11) by a service account and any
network logon (Logon Type 3) from a source host that is not the
authorized service host.


GENERAL RULES (apply to every service account)
----------------------------------------------

  RULE 1  Service accounts authenticate ONLY from their documented
          service host.  Cross-host use is anomalous.

  RULE 2  Service accounts authenticate ONLY as Logon Type 3 (Network)
          or Logon Type 5 (Service).  Logon Type 2 (Interactive),
          Logon Type 10 (RemoteInteractive / RDP) or Logon Type 11
          (CachedInteractive) by a service account is anomalous.

  RULE 3  Service accounts use Kerberos authentication against the
          domain.  NTLM authentication by a service account is
          anomalous (suggestive of pass-the-hash).

  RULE 4  Service account passwords are 24-character random, rotated
          every 180 days, and stored ONLY in the Active Directory
          Group Managed Service Account (gMSA) infrastructure where
          the account supports it.  No service account password is
          known to a human.

  RULE 5  Service accounts have the minimum rights required to run
          their service.  No service account is a member of Domain
          Admins, Enterprise Admins, or any other privileged built-in
          group.


SERVICE ACCOUNT INVENTORY
-------------------------

--- svc_healthsync ---

  UPN:                 svc_healthsync@meddefense.local
  Purpose:             Runs the health-record synchronization service
                       on SRV-HEALTH-DB.  The service replicates
                       patient record updates from the primary MS-SQL
                       database to the departmental reporting views.
  Authorized host:     SRV-HEALTH-DB (10.10.20.15)  -- SINGLE HOST
  Authorized logon:    Type 5 (Service) on SRV-HEALTH-DB
                       Type 3 (Network) from SRV-HEALTH-DB TO other
                         servers where the service fetches reference
                         data (SRV-FILE-01 for reference tables)
  NOT AUTHORIZED:      Any logon from any workstation host.
                       Any interactive (Type 2/10/11) logon from any
                         host.
                       Any NTLM authentication.
  Group membership:    meddefense\health_sync_svcs (custom group)
  Privilege scope:     Read/write on SRV-HEALTH-DB databases
                         (health_records, health_meta)
                       Read-only on SRV-FILE-01 \reference_tables
                       NO privileges on SRV-DC-01, SRV-INS-DB,
                         SRV-BACKUP-01 or any workstation host

HIGH-RISK ACCOUNT CALLOUT
-------------------------

Among the above accounts, svc_healthsync is the highest-risk account
from a confidentiality perspective.  It has read/write access to
all HIPAA-protected patient health records on SRV-HEALTH-DB.  Any
anomalous use of svc_healthsync must be treated as a potential PHI
exposure event from the first indicator and escalated to the CISO.


MONITORING GUIDANCE FOR THREAT HUNTERS
--------------------------------------

When hunting for service account abuse, the following jq query logic
applies to Windows Event 4624 (Successful Logon) records:

  -  The TargetUserName field matches ^svc_ (service account)
  -  The WorkstationName field matches ^WS-  (workstation source)
     ==> UNAUTHORIZED.  Every service account in this matrix has
         AUTHORIZED_HOST scoped to a specific server.  A workstation
         source indicates credential theft.

  -  The TargetUserName field matches ^svc_
  -  The LogonType is 2, 10 or 11 (Interactive, RemoteInteractive,
     CachedInteractive)
     ==> UNAUTHORIZED.  Service accounts authenticate only as
         Type 5 or Type 3 per RULE 2.

  -  The TargetUserName field matches ^svc_
  -  The AuthenticationPackageName is NTLM
     ==> UNAUTHORIZED.  Per RULE 3 service accounts authenticate
         with Kerberos; NTLM usage suggests pass-the-hash.


ACCOUNTS THAT DO NOT APPEAR IN THIS MATRIX
-------------------------------------------

If a threat hunt or alert surfaces an account starting with "svc_"
that is NOT listed in this matrix, it is itself an indicator.  A
legitimate service account must be documented here before it is
created in Active Directory.  An undocumented svc_* account is
either an operational process failure or an attacker-created
persistence account.

As of the effective date of this document, NO undocumented svc_*
accounts existed in the meddefense.local domain.  Any such account
appearing in data collected after 2026-04-01 is suspect.
