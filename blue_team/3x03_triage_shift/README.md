# 3x03 Triage Shift

MedDefense Health Systems — Module 3 capstone bridge project. Works the alert
queue produced by the 3x02 detection catalog: classifies every alert as
true positive, false positive, or benign, escalates true positives into
incident records, and rolls false-positive patterns into rule tuning
recommendations for the detection engineer.

## Environment variables

| Variable       | Default                                  | Points at                          |
|----------------|-------------------------------------------|-------------------------------------|
| `CATALOG_DIR`  | `~/3x02_package/detection_catalog`         | 3x02 detection catalog output       |
| `HANDOFF_DIR`  | `~/3x00_handoff/evidence_handoff`          | 3x00 evidence pipeline output       |
| `BASELINE_PKG` | `~/3x01_package/baseline_package`          | 3x01 baseline package output        |
| `ASSETS_DIR`   | `~/3x03_assets` (must be set manually)     | `ioc_context.json` for this project |
| `TRIAGE_PKG`   | `~/3x03_package/triage_package`            | this project's output directory     |

On the lab sandbox:

```
source ~/m3_env.sh
export ASSETS_DIR=$HOME/3x03_assets
```

## Local testing

This repository's copies of the upstream 3x00/3x01/3x02 outputs live flat at
the root of their own project directories rather than under the nested
`data/`, `context/`, `baselines/`, `alerts/` layout the lab sandbox provides.
`local_catalog/` mirrors that lab layout with symlinks back into
`../3x02_the_alert_factory/`, so scripts here can be exercised locally by
pointing `CATALOG_DIR` at it:

```
CATALOG_DIR="$(pwd)/local_catalog" ./0-queue_assessment.sh
```

`local_handoff/`, `local_baseline/` and `local_assets/` mirror `$HANDOFF_DIR`,
`$BASELINE_PKG` and `$ASSETS_DIR` the same way, for tasks that need them:

```
CATALOG_DIR="$(pwd)/local_catalog" \
HANDOFF_DIR="$(pwd)/local_handoff" \
BASELINE_PKG="$(pwd)/local_baseline" \
ASSETS_DIR="$(pwd)/local_assets" \
./2-context_assembly.sh
```

`local_assets/ioc_context.json` is hand-built (25 indicators, same reputation
mix as the real lab asset) since no upstream project produces it — it is a
read-only lab-provided input on the real environment.

The real committed `alert_queue.json` (from `3x02_the_alert_factory/`) only
has 2 alerts, generated by the 4 Sigma rules implemented so far, both below
the `critical` priority band and with no IP-bearing events. Batches 3 and 4
below therefore correctly produce empty ticket arrays against local data —
every matching predicate was verified independently against synthetic
alerts spliced into `enriched_queue.json` (see task descriptions). Real
grading/production runs use the lab-provided environment variables and the
full-scale queue (no override needed once `~/m3_env.sh` is sourced).

## Tasks

### 0. Queue Assessment — `0-queue_assessment.sh`

Reads `$CATALOG_DIR/alerts/alert_queue.json` and
`$CATALOG_DIR/alerts/alert_queue_schema.json`, validates every alert against
the schema, and writes `queue_assessment.json`:

- `queue_size`, `validation_errors`
- `by_priority_band` (critical >= 20, high 10-19, medium 5-9, low 1-4)
- `by_rule`, `by_hostname` (sorted descending by count)
- `by_attack_tactic` — derived from each source rule's Sigma `tags:` block
  (`$CATALOG_DIR/rules/sigma`, tuned variants override base rules); alerts
  whose rule cannot be located are counted under `unmapped`
- `time_span` (first/last `event_summary.timestamp`)
- `top_targets` — top 3 hosts by cumulative `priority_score`

Also prints a human-readable shift briefing to stdout. The queue's own
`generated_at` values (not wall-clock "today") anchor the briefing date, so
both the JSON output and the printed briefing are deterministic for a given
input queue.

### 1. Triage Methodology Definition — `triage_methodology.md`

One-page, ~390-word written policy: classification taxonomy (with examples
drawn from the 4 committed Sigma rules), priority ordering rule, evidence
requirement, escalation criteria, SLA per priority band, and the
documentation checklist every ticket must satisfy. Belongs at
`triage_package/spec/triage_methodology.md` in T14.

### 2. Context Assembly — `2-context_assembly.sh`

Reads `alert_queue.json`, `$HANDOFF_DIR/context/asset_inventory.json`,
`$HANDOFF_DIR/data/enriched_events.json`, `$BASELINE_PKG/baselines/baseline_summary.json`
and `$ASSETS_DIR/ioc_context.json` once, and writes `enriched_queue.json`
where every alert additionally carries:

- `asset` — merges the `asset_inventory.json` record (ip, criticality,
  data_classification, owner, business_impact_multiplier) with `role` and
  `network_zone` from the matched event's own embedded `asset` sub-object
  (enriched_events.json already carries per-event role/zone context; the
  standalone inventory file in this repo does not, so the two are merged)
- `baseline_host_profile` — per-host `auth`/`process`/`network`/`file`
  slices from `baseline_summary.json` (network is looked up by the host's
  own IP, since that section is keyed by `per_src_ip`)
- `event_record` — the full enriched event
- `ioc_hits` — `ioc_context.json` entries matched on `src_ip`/`dst_ip`,
  each carrying `ioc_flag: true` when `reputation != clean`
- `priority_band` — derived from `priority_score` (same bands as T0)

**event_ref caveat:** `event_ref` ("line:N", 0-indexed) was captured against
`normalized_events.json` at alert-generation time. Cleaning between
normalize and enrich drops/quarantines some records, so line N in
`enriched_events.json` is not guaranteed to be the same event (verified:
~134 lines drift over the real dataset). `event_record` is therefore
resolved by a composite content key (timestamp, hostname, user,
process_name, src_ip, dst_ip, event_category) built from `event_summary`,
not by reopening the line offset.

`service_account_prefix` / `management_subnets` are optional inventory-wide
settings some lab deployments attach to `asset_inventory.json`; this repo's
local fixture doesn't declare them, so the FP signatures that depend on
them (T4) degrade gracefully with a stderr warning instead of matching.

### 3. Batch 1: Clear-Cut True Positives — `3-triage_clearcut_tp.sh`

Reads `enriched_queue.json`, escalates every alert where `priority_band ==
critical`, at least one `ioc_hit.reputation == malicious`, and the rule's
category (derived from `event_summary.event_category`) shows a baseline
violation — defined as the observed action/process/port having zero
occurrences in that host's baseline window (the same "never seen before"
condition `baseline_summary.json`'s own `thresholds.unknown_process_penalty`
/ `unknown_port_penalty` score). Writes `tickets/batch1_clearcut_tp.json`;
`evidence_refs` includes the alert's own `event_ref` plus any other alert on
the same host within a 1-hour window ("linked correlation primitives").

### 4. Batch 2: Clear-Cut False Positives — `4-triage_clearcut_fp.sh`

Reads `enriched_queue.json` and `$HANDOFF_DIR/context/asset_inventory.json`
(for the two inventory-wide settings above), and closes every alert
matching any of the four FP signatures from the methodology
(`service_account_activity`, `management_subnet`, `baseline_match`,
`clean_ioc_no_deviation`), tagging each ticket's `fp_reason` for T10.
Writes `tickets/batch2_clearcut_fp.json`.
