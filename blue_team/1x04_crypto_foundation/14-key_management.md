| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **TPM (Trusted Platform Module)**                               | A small, dedicated security chip soldered onto (or firmware-integrated into) a device's motherboard, providing hardware-anchored cryptographic functions and secure storage for a limited set of keys                                                                                                                                                                                                        | Full-disk encryption keys (e.g., BitLocker's key sealed to a TPM), device boot integrity (Secure Boot measurements), and platform identity fundamentally a*single-device* trust anchor | Effectively free built into nearly every business laptop/desktop sold since ~2016, no separate purchase                                                                  | Employee laptops and desktops; ties directly into this project's Task 13 recommendation for full-disk encryption on MedDefense laptops, where a TPM would seal the disk encryption key to that specific physical machine                                                                                       |

| **Secure Enclave**                                              | An isolated, hardware-enforced execution environment within a device's main processor (e.g., Apple's Secure Enclave, Intel SGX) that runs sensitive operations in memory inaccessible even to the device's own operating system kernel                                                                                                                                                                       | Biometric data templates, device-specific encryption keys, and sensitive computations that need to run in isolation from a potentially compromised OS                                     | Built into the processor/device no separate purchase, but only available on hardware that includes the feature                                                           | Consumer and mobile devices (e.g., an iPhone's Face ID data, or a workstation running sensitive local computations) less directly applicable to MedDefense's server-side infrastructure than TPM or HSM, but relevant if MedDefense ever builds a patient-facing mobile app handling biometric authentication |

## Part 2: MedDefense Key Management Design

MedDefense now has at least four distinct encryption keys in active use across this project: the **EHR database encryption key** (Task 13), the **`NAS-01` backup volume key** (Task 12), the **patient portal's TLS private key** (Task 10), and the **VPN tunnel keys** (site-to-site IPSec, referenced throughout Task 0/4). The plan below addresses each using the governance structure already established in 1x03.

**Where each key is stored:**

- **EHR database key:** a cloud HSM-as-a-Service instance (per Part 1/3), never on `ehr-srv-01` or `ehr-db-01` themselves this directly avoids repeating the exact mistake Task 0/12 already flagged for `NAS-01` (never store the key on the same system the data lives on).
- **Backup volume key:** the same HSM instance (or a dedicated secrets vault distinct from `NAS-01`), per Task 12, Part 4's explicit requirement that the key never sit on the NAS itself.
- **Portal TLS private key:** held on `web-srv-01` itself (this is the one key in this list where co-location with the protected system is the industry-normal and accepted pattern, since a TLS private key must be locally accessible to the web server process for every handshake) but access to the underlying filesystem location is restricted to the service account the web server runs as, and the key is never committed to version control (directly the failure mode described in 1x03's MCQ T25 Git-exposure scenario, referenced again in Task 9, Part 3).
- **VPN tunnel keys:** held on the FortiGate appliances at each site, consistent with how site-to-site IPSec is normally managed the key risk here is not where the key lives but the compromised Westside consumer-router endpoint (Task 0/4), which is an endpoint-hardening problem, not a key-storage problem.

**Who has access to each key**, using the RACI/data-role structure from 1x03's governance work:

- **Sarah Park (IT Director, Data Custodian)** day-to-day operational access to rotate and deploy the backup volume key and the portal TLS key, consistent with her existing Custodian role for backups, access control, and encryption implementation.
- **Security Analyst** supporting access to the EHR database key and HSM configuration, mirroring the "Responsible" support role already assigned to the analyst elsewhere in the RACI matrix.
- **James Chen (Deputy CISO)** Accountable for key management policy and any decision to revoke/rotate a key outside the normal schedule, matching his standing Accountability for the security program overall.
- **No single individual holds unrestricted access to all four keys simultaneously** this is a deliberate separation-of-duties control, since the entire point of centralizing keys in an HSM/KMS is defeated if one compromised account can extract everything it protects.

**Key rotation frequency and process:**

- **EHR/billing database keys:** rotated annually at minimum, or immediately upon any suspected compromise, via the HSM's native key-rotation feature (re-encrypting data under a new key without ever exposing the old or new key outside the HSM).
- **Backup volume key:** rotated annually, coordinated with a verified test restore (per 1x03's backup-verification control) to confirm the new key works before the old one is retired.
- **Portal TLS private key:** rotated every ~90 days as a byproduct of the certificate lifecycle already built out in Task 10 a new key is generated with every CSR/renewal cycle, so rotation is inherently frequent and automatic rather than a separate manual process.
- **VPN keys:** rotated per FortiGate's standard IKE rekey interval (automatic, typically hours, for the session keys) with the underlying pre-shared/certificate material reviewed annually or immediately if the Westside endpoint's integrity is ever in question.

**If a key is compromised:** immediately revoke and rotate that specific key through the HSM/KMS (which supports exactly this operation without needing to touch the other three keys), re-encrypt any data protected by it, and treat the event as a security incident requiring root-cause investigation directly mirroring the exact revocation sequence already built out for a compromised TLS private key in Task 9, Part 3, generalized to any key in this plan.

**If a key is lost (not compromised, simply unrecoverable):** for the database and backup keys, this is catastrophic and unrecoverable by cryptographic design (Task 12, Part 4) the mitigation is **key escrow**: a securely stored secondary copy of each key (or, more precisely with a proper HSM, redundant HSM instances/backup key material managed through the HSM vendor's own secure backup mechanism, never a plaintext copy sitting in a file) held separately from the primary, so no single point of failure can destroy both the data and its only key simultaneously. James Chen, as Accountable owner, should hold final authority over who can invoke escrow recovery, with the action logged and reviewed access to the recovery mechanism itself must be as tightly controlled as access to the key it recovers, or the escrow copy simply becomes a second, weaker copy of the same key.

## Part 3: The HSM Decision

**Estimated cost:** at roughly $1-2 per key per month for a cloud HSM-as-a-Service, and counting the four key categories above (EHR database, backup volume, portal TLS, plus reasonable headroom for a handful of additional keys as VPN/CA material is centralized over time call it 8-10 keys total to be conservative), the estimated annual cost is:

```
10 keys x $2/key/month x 12 months = $240/year
```

**Risk comparison using the Risk Register's real, quantified figures (1x03):** the risk register's most directly relevant entry is **RISK-001 (Ghostcat exposes EHR DB credentials)**, with an **ALE of $495,000** before treatment and a **residual ALE of $24,750** after the primary mitigation (patching/credential rotation) is applied. This is the strongest available proxy in the register for "what does unauthorized access to the EHR database cost MedDefense in a year, on average" and per Task 13's recommendation that the EHR database itself be protected with database-level encryption, the encryption key *is* now effectively as valuable a target as the database credentials RISK-001 already quantifies: if that key is stored insecurely (e.g., in a plaintext config file on `ehr-srv-01` itself, the exact anti-pattern this task's own context section opens with) and compromised, the practical consequence an attacker with full read access to the patient database is the same regardless of whether they got there via a Ghostcat-style credential exposure or a poorly-secured encryption key.

**Is the investment justified?** Overwhelmingly yes, and by an unusually wide margin even for this project: **$240/year in HSM cost against a risk category quantified at $495,000 (or even the already-mitigated residual of $24,750) is a cost-to-risk ratio of roughly 1:100 to 1:2,000** several orders of magnitude more favorable than any control evaluated in the 1x03 cost-benefit analysis. The HSM does not replace the credential/patching fix RISK-001 already prescribes, but it directly closes the specific failure mode this task's own opening context describes encrypting data and then defeating that encryption by mishandling the key — for a cost low enough that "we couldn't afford it" is not a credible objection at MedDefense's $120,000 total security budget scale. **Recommendation: adopt a cloud HSM-as-a-Service immediately** for the database and backup keys identified in Part 2, funded easily within the remediation budget alongside the higher-cost controls (SIEM, MFA) already prioritized in 1x03's roadmap.
