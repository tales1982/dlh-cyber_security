## Part 1: Technique Comparison

| Technique               | What it does to the data                                                                                                                                             | Can the original be recovered, and by whom?                                                                                                                                                | Concrete healthcare use case                                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Encryption**    | Transforms plaintext into ciphertext using a reversible mathematical algorithm and a key                                                                             | Yes anyone holding the correct decryption key can fully recover the original data                                                                                                         | Protecting the EHR database backup on`NAS-01` at rest, so a stolen drive yields only ciphertext without the key (Task 0 gap)                              |
| **Hashing**       | Transforms input into a fixed-size digest using a one-way function                                                                                                   | No by design there is no key or process that reverses a hash back to its input; only pre-computed/dictionary matching can recover a hash-to-input mapping if the input was guessable      | Storing a verification value for a file's integrity (Task 3's`3-hash_verify.sh`) or a password's hash (never the password itself)                         |
| **Tokenization**  | Replaces a sensitive value with a randomly generated, non-mathematically-related surrogate value (a "token"), keeping the real value in a separate secured vault     | Yes, but only by whoever holds access to the token vault that maps token back to real value the token itself carries zero information about the original                                  | Replacing a patient's full credit card number in the billing system with a token that has no computable relationship to the real card number (Part 2 below) |
| **Data Masking**  | Partially obscures a value (commonly by replacing some characters with a fixed symbol) while preserving the original format/length                                   | Partially the visible remaining characters are real; the masked portion is simply not shown to that viewer, though it typically still exists in the underlying record for authorized roles | Showing a receptionist`***-**-4321` for a patient's SSN instead of the full number (Part 3 below)                                                         |
| **Steganography** | Hides an entire secondary payload inside the unused/low-significance bits of a legitimate-looking cover file (image, audio, document) so its presence is not obvious | Yes, fully but only by someone who knows a payload is embedded and has the extraction method/key; to anyone else the cover file appears completely ordinary                               | Both a legitimate covert-channel protection technique and as Part 4 covers a data exfiltration threat vector via DICOM images                             |

## Part 2: MedDefense Tokenization Design

**What data is tokenized, and token format:** The full 16-digit credit card Primary Account Number (PAN) is tokenized. The billing system stores a token in the same format as a PAN (16 digits, potentially preserving the real card's first 6 digits the BIN/IIN and last 4 digits, e.g. `453922••••••1147`), so downstream billing code and reports that expect a card-number-shaped string continue to work unmodified a common "format-preserving tokenization" pattern that avoids requiring database schema or validation-logic changes throughout the billing application.

**Where the vault lives and how it's protected:** The token-to-PAN mapping vault is a dedicated, isolated database (not `billing-srv-01`'s existing MySQL instance, which Task 0 already documented as unencrypted and reachable in plaintext) ideally a purpose-built tokenization service or a hardened, network-segmented vault host with no other role. Protection layered on it: the PAN values inside the vault are themselves encrypted at rest with AES-256 (Task 1), the encryption key is held in a dedicated key-management system (HSM or cloud KMS) separate from the vault's own storage directly avoiding the exact mistake Sarah flagged for `NAS-01` in Task 0 ("if we encrypt the backups and store the key on the same NAS, we lose both together") and access to detokenize (retrieve the real PAN from a token) is restricted to a minimal, logged, individually-authorized set of service accounts, never to interactive human logins. Network access to the vault should be limited to the specific billing application service account, over an authenticated, encrypted connection, with all detokenization calls logged to the SIEM.

**If the token vault is compromised:** An attacker who steals the *billing database* (with tokens in place of real PANs) gains nothing usable the tokens are random values with no mathematical path back to a real card number, unlike an encrypted value which remains attackable if the key is ever also exposed. An attacker who compromises the *vault itself* is a much more serious event, since the vault is the only place the token-to-PAN mapping exists but because the PAN values inside the vault are also encrypted with a separately-held key, compromising the vault's storage alone (without the key) still does not yield usable card numbers; the attacker would need to compromise both the vault database and the separate key-management system, a materially higher bar than compromising a single unencrypted database.

**Tokenization vs. simply encrypting the PANs:**

- **Advantage of tokenization:** the billing database itself (and every report, log, or export built from it) never contains anything cryptographically related to the real PAN encryption always keeps the *ciphertext* of the real value sitting right next to wherever it's used, meaning every system that touches billing data becomes part of the encryption key's blast radius if compromised. Tokenization confines that blast radius to the vault alone.
- **Advantage of tokenization for compliance scope:** PCI-DSS scope (the compliance framework governing card data specifically) shrinks dramatically systems that only ever see tokens are largely out of PCI-DSS scope, while systems that hold encrypted PANs (even if the key is elsewhere) generally remain in scope because the ciphertext is still classified as cardholder data.
- **Disadvantage of tokenization:** it requires operating and securing an additional service (the vault) rather than reusing existing encryption infrastructure, and every system needing the *real* PAN (e.g., actually submitting a charge to a payment processor) must call out to the vault to detokenize, adding an operational dependency and a network round-trip that a locally-held encryption key would not require.
- **Net recommendation for MedDefense's billing use case:** tokenization is the better fit specifically *because* payment processing is not billing's core competency MedDefense's billing system needs to reference a card for recurring/repeat charges, not perform novel cryptographic operations on it, which is exactly the narrow, vault-mediated access pattern tokenization is designed for.

## Part 4: Steganography as Threat Vector

DICOM medical images are ideal steganographic carriers precisely because of the properties that make them clinically useful: they are large (often tens to hundreds of megabytes per study), contain enormous amounts of pixel data with imperceptible bit-level redundancy, and move between MedDefense and outside facilities routinely and expectedly as part of normal patient-referral workflows meaning a large binary file leaving the network raises no inherent suspicion the way a large text or database export would. A malicious insider with legitimate PACS access (already a documented weak point via the shared-login finding in 1x03's risk register) could embed exfiltrated data patient records, billing data, or credentials into the least-significant bits of a routine DICOM image's pixel data, or within its metadata/private tag fields, then send that image to an external facility, an email attachment, or removable media through channels the organization already permits for legitimate imaging transfers. This is dramatically harder to detect than traditional exfiltration because content-based data loss prevention tools are built to pattern-match recognizable sensitive strings (SSNs, MRNs, credit card formats) inside text, not to statistically analyze whether a binary image file's pixel noise has been subtly altered the DICOM file that left the building looks, to every conventional DLP scanner, identical to the thousands of legitimate DICOM transfers that happen every week. The control most likely to help here is not content inspection at all but the **SIEM deployment (Wazuh) and network-monitoring capability from the 1x03 strategy (RISK-002, CIS Control 13)** behavioral/volume-based anomaly detection that flags *unusual transfer patterns* (an account suddenly exporting far more imaging data than its historical baseline, transfers to unfamiliar external destinations, or transfers occurring outside that user's normal working hours) rather than trying to inspect the hidden content itself, which is exactly the kind of detective control this project has already prioritized for the EHR export function and could reasonably be extended to cover PACS/DICOM egress as well.
