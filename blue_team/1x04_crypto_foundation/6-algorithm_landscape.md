## MedDefense Crypto Gap Analysis

Comparing what Task 0's audit notes and the 1x02 vulnerability findings show MedDefense **actually running** against what this table recommends surfaces the same handful of root causes repeating across multiple systems:

**1. DES enabled for Kerberos (1x02 Finding 018) → disable DES encryption types entirely.** MedDefense's domain controllers (`ad-dc-01`/`02`) still permit DES as a Kerberos encryption type. DES is not merely outdated, it is exhaustively brute-forceable there is no "reduced risk" version of running it. **Recommendation:** disable DES and RC4 Kerberos encryption types domain-wide via the `msDS-SupportedEncryptionTypes` attribute and Group Policy, enforcing AES128/AES256-only Kerberos tickets, which every modern Windows client and the domain controllers themselves already support.

**2. RC4 enabled for Kerberos (1x02 Finding 018) → same fix as above, same urgency.** RC4's presence is what makes Kerberoasting practical against any service account still permitted to negotiate it (demonstrated mathematically in Task 3, Part 2): an attacker requests an RC4-encrypted service ticket, takes it offline, and cracks it with GPU-scale speed against the account's NTHash-derived key, with zero further contact with the domain controller. **Recommendation:** identical to DES disable RC4 as a supported Kerberos encryption type, and additionally audit all service accounts for `AS-REP roasting` exposure (accounts without Kerberos pre-authentication).

**3. TLS 1.0 supported on the Patient Portal (1x02 Finding 005) → disable TLS 1.0/1.1, enforce TLS 1.2 minimum with 1.3 preferred.** TLS 1.0 is vulnerable to BEAST, POODLE, and Lucky Thirteen, and it cannot negotiate the modern AEAD cipher suites (AES-GCM, ChaCha20-Poly1305) or ECDHE-based forward secrecy that this table recommends. **Recommendation:** reconfigure `web-srv-01`'s Apache TLS settings to support TLS 1.2 and 1.3 only, with a cipher suite list restricted to ECDHE key exchange plus AES-GCM/ChaCha20-Poly1305 directly feeding into the certificate renewal work in Tasks 8-10.

**4. AD's default NTHash (MD4-family) credential storage (Task 0 finding) → cannot be eliminated outright, but its blast radius must be reduced.** Unlike the three cases above, NTHash cannot simply be "disabled" without breaking NTLM compatibility that legacy systems may still require but MD4 is fully broken, unsalted, and trivially crackable if `NTDS.dit` is ever exfiltrated (the same offline-cracking risk pattern as Kerberoasting). **Recommendation:** audit and eliminate any remaining NTLM dependency wherever possible so NTLM (and therefore NTHash) can be disabled domain-wide per interface/system; where legacy compatibility genuinely requires it, treat `NTDS.dit` and `ad-dc-01`/`02` as maximum-sensitivity assets requiring the strictest access controls and monitoring available, since the underlying hash algorithm itself offers no protection if that boundary is crossed. Separately, this is unrelated to and does not excuse weak **application-level** password storage those systems should independently use Argon2 (per the Key Derivation table above), not rely on AD's NTHash as their security boundary.
