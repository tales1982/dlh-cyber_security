# 13. The Encryption Levels MedDefense Health Systems

**Analyst:** Security Analyst
**Date:** Current

## Encryption Levels Comparison

| Level               | Scope                                                                                                                                  | Performance Impact                                                                                                                                                                                                                                            | Key Management                                                                                                                                                                                    | Use Case                                                                                                                                                                                                                                                                                                                                                    |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Full-disk** | Entire physical or virtual disk, including the OS, swap, and temp files                                                                | Low encrypts/decrypts transparently at the block layer, with modern AES-NI hardware bringing overhead close to the AES-256-CBC/XTS throughput measured in Task 1 (~1.7+ GB/s)                                                                                | Simplest of the six: one key/passphrase unlocks the entire disk, typically entered once at boot (e.g., BitLocker, LUKS demonstrated in Task 12)                                                   | **Best choice when protecting against physical device theft/loss** a stolen laptop or drive is unreadable without the key, but anything with legitimate OS-level access sees all data in the clear                                                                                                                                                   |
| **Partition** | One logical partition on a disk (not the whole physical device)                                                                        | Similar to full-disk same underlying block-level mechanism, just scoped narrower                                                                                                                                                                             | Same simplicity as full-disk, one key per partition; multiple partitions on one disk can have independent keys                                                                                    | **Best choice when only part of a disk needs protection** (e.g., a sensitive data partition separate from a shared/less-sensitive OS partition on the same physical drive)                                                                                                                                                                            |
| **Volume**    | A logical volume, which may span multiple physical disks (e.g., LVM, a RAID array, or a virtual disk image like Task 12's loop device) | Comparable to full-disk/partition still block-level, still benefits fully from AES-NI                                                                                                                                                                        | Same model as full-disk: one key unlocks the logical volume regardless of how many physical disks back it                                                                                         | **Best choice for storage that spans or abstracts physical disks** exactly NAS-01's RAID-5 array (Task 12, Part 4), where the logical volume, not any single physical disk, is the natural encryption boundary                                                                                                                                       |
| **File**      | Individual files, selected independently of what disk/volume/database they sit in                                                      | Low per-file, but operationally inconsistent protection depends entirely on every application/user remembering to encrypt each sensitive file individually                                                                                                   | More complex: potentially a different key per file or per user, requiring a key-tracking system so files remain decryptable later                                                                 | **Best choice for selectively protecting specific sensitive files that travel independently of their storage** (e.g., an email attachment, a document shared outside the encrypted volume it originated on) a poor choice as the *only* layer for systematic, whole-system protection, since it depends on consistent human/application discipline |
| **Database**  | An entire database or tablespace (e.g., PostgreSQL's Transparent Data Encryption equivalent, or full-tablespace encryption)            | Moderate every read/write to the database engine passes through encryption/decryption, adding overhead beyond pure disk I/O, though modern database engines optimize this significantly                                                                      | Managed by the database engine itself or a dedicated database encryption key, often integrated with an external KMS/HSM (Task 14)                                                                 | **Best choice when the threat model includes disk-level attacks against database files but legitimate application queries still need full, unencrypted access to run normal SQL** protects backups/stolen disks without breaking query functionality                                                                                                 |
| **Record**    | Individual fields or records within a database (e.g., only the SSN column, not the whole row/table)                                    | Highest per-operation cost of the six every query touching an encrypted field requires encryption/decryption at the application or database function level, and encrypted fields generally cannot be indexed or searched efficiently in their encrypted form | Most complex: typically requires application-layer key management (or a database feature like column-level encryption), with careful handling of which application roles can decrypt which fields | **Best choice when different specific fields need different access restrictions from different roles** directly relevant to Task 7's data-masking design, where an SSN column needs tighter access control than the rest of a patient record, at the cost of breaking normal indexing/search on that field                                           |

## MedDefense Encryption Level Map

| Data Store                                                | Recommended Level                                                                                                        | Justification                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Patient records in PostgreSQL (`ehr-db-01`)**   | **Database-level** (with record-level for the highest-sensitivity fields specifically, e.g., SSN)                  | The EHR application needs to run normal clinical queries across full patient records constantly database-level encryption protects the data files/backups from disk-level exposure (Task 0's finding of zero at-rest protection) without breaking that query pattern; layering record-level encryption on top for a small number of especially sensitive fields (SSN) adds the extra access-restriction Task 7's masking design already called for, without paying record-level's full performance cost across the*entire* database.                                                                                                                                                                                                                                                                                                                                                                                               |
| **Backup data on `NAS-01`**                       | **Volume-level**                                                                                                   | Exactly the design built out in Task 12, Part 4 NAS-01's RAID-5 array is the natural logical-volume boundary, and volume-level encryption transparently protects every backup format (PostgreSQL dumps, MySQL dumps, file-based Veeam backups) without requiring each backup job to individually implement its own encryption.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Financial records in MySQL (`billing-srv-01`)** | **Database-level, plus tokenization for card data specifically (not encryption at all for that subset — Task 7)** | Same reasoning as the EHR: billing queries need full, unencrypted-at-the-query-layer access to run normal operations, so database-level encryption is the right baseline but the specific credit card PAN data should not be encrypted at all in this database, it should be**tokenized** (Task 7, Part 2), since Task 7 already established that tokenization keeps actual cardholder data out of this database's compliance scope entirely, which plain database-level encryption cannot do.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Medical images on PACS (`pacs-srv-01`)**        | **Volume-level**                                                                                                   | DICOM images are stored as discrete files on a storage array, not database rows PACS systems manage images as a file-based archive rather than a relational database, so "database-level" doesn't map cleanly here. Encrypting at the volume boundary (matching the NAS-01 logic from Task 12, Part 4) gives one key that transparently covers every image on the array with no per-file discipline required from radiology staff; file-level is rejected as the*primary* control here because relying on every study being individually encrypted would repeat the same "depends on human/application discipline" weakness the File row already flags, and this dataset is large and uniform enough that a single volume boundary is both sufficient and far lower-overhead.                                                                                                                                                      |
| **Email data in O365**                              | **File-level**                                                                                                     | Task 0 already found the underlying platform storage is Microsoft-managed and adequately protected (BitLocker + per-mailbox encryption), so the gap MedDefense must close is specifically individual messages containing PHI being sent in plaintext (per Sarah's note). A message is a discrete, independently-shared unit of data selected by the sender rather than a whole disk/volume/database boundary exactly the File-level definition in this table (individual files, selected independently of what disk/volume/database they sit in) so S/MIME or Office Message Encryption, applied per-message, is the closest fit of the six levels, not a hybrid.                                                                                                                                                                                                                                                                    |
| **Employee laptops**                                | **Full-disk**                                                                                                      | Laptops are the textbook full-disk use case: the realistic threat is device theft/loss (an employee's bag stolen from a car, a laptop left on a train), not a targeted attack against one file while the OS is running full-disk encryption (e.g., BitLocker, LUKS as demonstrated in Task 12) protects everything on the device with the single lowest-friction key-management model, appropriate for a fleet of devices IT needs to manage centrally without per-file complexity.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **BD Alaris pump firmware/configuration**           | **Full-disk**                                                                                                      | These are embedded, resource-constrained clinical devices, not general-purpose servers the entire firmware/configuration image is a single flat storage blob with no separate OS/data partitions to distinguish, so full-disk is the correct fit rather than partition-level, which only makes sense when a device has multiple independently-owned partitions to choose between. The goal is protecting the whole image from extraction/tampering if a device is physically accessed, not selective field-level protection (there's no equivalent of "run a SQL query against a live infusion pump"); the earlier ECC recommendation for these devices (Task 2, Part 2, given their limited CPU/battery) applies here too favor whatever full-device encryption mechanism the vendor's constrained hardware can actually support efficiently over a heavier database/record-level scheme these devices were never designed to run. |
